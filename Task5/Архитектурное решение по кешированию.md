# Архитектурное решение по кешированию

Раз жалобы сейчас идут на медленную работу MES. Значит с ним и предстоит работать, а так же с системами, которые с ним взаимодействуют и тем самым могут нагружать.

## Мотивация

В описании к задаче существует две проблемы:
- Операторы жалуйста на медленную работу с дашбордом. Исправив это, мы сможем повысить их производительность и удовлетворенность работой.
- Клиентов не устраивает скорость выполнения заказа. Исправив это, мы сможем повысить их удовлетворенность и лояльность.

Компоненты системы:
- MES API - кэшируется список заказов для операторов. Высокий приоритет.
- MES API - кэшируется результат рассчета стоимости. Высокий приоритет.
- Shop API - кэшируется информация о заказе. Низкий приоритет.

## Предлагаемое решение

### Кэширование списка заказов в MES-API

Серверное кеширование через Redis. Так как инвалидация списка заказов будет происходит на уровне бизнес логики (изменение статуса заказа) и данные слишком динамичные.

Тип кэширования сложный вопрос, тк есть пагинация и фильтрация. Можно использовать гибридный подход:
- Для частозапрашиваемых страниц использовать Write-Throught
- Для остальных случаев использовать Cache-Aside (или ничего, тк они не часто читаемые)

Write-Throught убирает вероятность гонки, которая может возникнуть в Cache-Aside,когда кэш еще не создан, все запросы идут в БД.

Инвалидация данных происходит в любом случае, при любом изменении статуса заказа.

Refresh-Ahead не дает преимуществ, тк по сути просто является самообновляемым кэшем с TTL и при инвалидации ему понадобится время, чтобы закэшировать данные снова.

### Кэширование результата расчета стоимости в MES-API

Write-Throught - для определенного ключа после рассчета стоимости кэшируется результат для конкретной 3d модели, в случае повторного запроса с такими же параметрами выдается закэшированный результат.

## Стратегия инвалидации

### Список заказов и данные конкретного заказа

Выбрана программная инвалидация.

При любом изменении статуса заказа MES API явно удаляет соответствующие ключи из Redis:
- Ключ конкретного заказа: `order:{order_id}`
- Ключи списков заказов затрагивающих изменённый статус: `orders:status:{new_status}` и `orders:status:{old_status}`
  
Это гарантирует, что после смены статуса операторы увидят актуальные данные при следующем запросе.
 
Почему не временная инвалидация:

Операторы конкурируют за заказы — устаревший список даже на 30 секунд означает что оператор видит заказ, который уже взял другой.
 
## Результат расчёта стоимости

Выбрана временная инвалидация.
 
Расчёт привязан к хэшу 3D-модели: `price_calculation:{md5_hash}`. Модель не меняется — результат стабилен. TTL 30 дней как защита от накопления устаревших данных по неактуальным моделям. Программная инвалидация не нужна — если модель изменилась, хэш изменится и это будет новый ключ.
