# Анализ требований к системе «Александрит»

## Проблемные места

- Расчёт стоимости занимает от 2 до 30 минут — при росте нагрузки заказы накапливаются в очереди
- Нет понимания, где пропадают или задерживаются заказы — отсутствует трекинг и наблюдаемость
- Дашборд операторов в MES медленно загружается
- MES DB работает в одном инстансе на чтение и запись — нет read-реплики
- MES API работает в одном инстансе — нет отказоустойчивости и горизонтального масштабирования
- Задержка релиза достигает месяца из-за ручного E2E-тестирования
- Нет rate limiting на публичном API — внешние партнёры могут перегрузить систему
- RabbitMQ не настроен для надёжной доставки: нет DLQ и retry-логики — сообщения теряются при сбоях

## Инициативы по улучшению

1. **Мониторинг и трейсинг flow заказа** — настроить distributed tracing через каждый этап статуса заказа и алерт, если заказ не сменил статус дольше ожидаемого; без этого любое дальнейшее исправление — гадание
2. **RabbitMQ: DLQ + retry + алерт** — настроить Dead Letter Queue, политику retry с exponential backoff и алерт на рост очереди мёртвых сообщений; наиболее вероятная причина потерь заказов прямо сейчас, исправление занимает несколько дней
3. **Автоматизировать E2E-тесты** на критических сценариях (создание заказа, расчёт стоимости, смена статуса, попадание в MES); если наш QA не справляется в одиночку — нанять фрилансера на проектную настройку, пока он обучается; без этого скорость доставки исправлений в продакшн остаётся низкой
4. **Увеличить количество инстансов MES API** — для отказоустойчивости и параллельного расчёта стоимости; при этом нужна координация задач через очередь, чтобы два инстанса не взяли один заказ на расчёт одновременно
5. **Дашборд операторов** — проверить запросы и индексы (в первую очередь по `status` + `created_at`), при необходимости добавить read-реплику MES DB; альтернативный подход — поменять процесс: заказ назначается оператору автоматически (push-модель), приоритет получает тот, кто первым освободился
6. **Добавить rate limiting на публичный API** — ограничить нагрузку от внешних партнёров по клиенту
7. **Кэш результатов расчёта стоимости** — при получении идентичной 3D-модели (по хэшу) не пересчитывать стоимость повторно; особенно актуально для сложных моделей с расчётом до 30 минут

## Целевая архитектура через полгода

Кардинальной перестройки не планируется — команда небольшая, бизнес теряет контракты прямо сейчас. Цель: стабилизировать текущую систему и убрать главные точки отказа.

**Что изменится:**
- RabbitMQ настроен с DLQ, retry и алертингом — заказы перестают теряться
- Весь flow заказа покрыт трейсингом — любая пропажа заказа видна в мониторинге
- MES API работает на нескольких инстансах с координацией задач расчёта через очередь
- MES DB получает read-реплику — дашборд читает с неё, записи идут на мастер
- Публичный API закрыт rate limiting-ом по клиенту
- E2E-тесты на критических сценариях автоматизированы, цикл релиза сокращён

**Следующий горизонт (не входит в полгода):**
- Push-модель назначения заказов операторам
- Кэш результатов расчёта стоимости

## Приоритет на ближайшие полгода

Из всех инициатив три имеют наивысший приоритет:

1. **Мониторинг и трейсинг** — без инструмента диагностики остальные исправления могут бить мимо
2. **RabbitMQ: DLQ + retry + алерт** — наиболее вероятная причина потерь заказов; дешёвое и быстрое исправление с немедленным эффектом
3. **Автоматизация E2E-тестов** — пока релизный цикл занимает месяц, любые исправления не доходят до пользователей вовремя; это разблокирует все последующие улучшения
