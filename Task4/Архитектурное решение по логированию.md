# Архитектурное решение по логированию

## Логи

### Уровень INFO
Логируем только критический путь заказа — изменение состояния заказ.
Поля: timestamp, service, order_id, correlation_id, previous_status, new_status, initiated_by

initiated_by — кто или что инициировало изменение: идентификатор пользователя (оператор, менеджер), системы (api_partner, system) или процесса (worker, consumer).

Приоритет внедрения: MES API → CRM API → Shop API. Через MES проходит основной путь заказа и работают API-партнёры.

### Уровень ERROR

Любая ошибка в системе, независимо от источника — HTTP, консьюмер, крон, воркер.

- Обязательные поля: timestamp, service, error_message, stack_trace
- Если доступен контекст запроса: correlation_id
- Если ошибка связана с заказом: order_id, описание того, что должно было быть выполнено

### Уровень DEBUG

Используется только в dev и release окружениях. В prod отключён, но может быть включён временно через конфиг без перезапуска сервиса — для диагностики живых инцидентов. Включает детали запросов к БД, тела HTTP-запросов, промежуточные состояния расчёта стоимости. Тела запросов логируются только после проверки на отсутствие персональных данных.

Приоритет низкий. Хотя тут вопрос, если сейчас происходит разбор ошибок вместе с пользователем, то может быть стоит продумать логирование тела запроса для управления заказами, чтобы сразу пробовать воспроизводить ошибку?

## Мотивация

Как было сказано, сейчас выявление инцидента происходит через общение с пользователем через тикеты тех поддержки. В случае добавления логирования, мы сможем реагировать на инцидент сразу как он произошел (появившуюся в логах ошибку). В случае, если ситуация не предвиденная, то мы сможем найти ошибку по логам.

### Метрики

1. MTTR (время восстановления после инцидента)
2. Нагрузка на поддержку
3. Процент заказов, доставленных в срок
4. Количество повторных обращений по одному инциденту
5. Время обнаружения аномалий

### Приоритеты

MES API → CRM API → Shop API

Через MES проходит основной путь заказа и работают API-партнёры. Поэтому начинать стоит с него.

CRM API — следующий по важности, тк он тоже задействуется всегда вне зависимости от источника заказа

Так же думаю было бы полезным во фронтовые сервисы добавить логирование ошибок. Это быстрое решение, но менее приоритетное, тк сейчас проблема с бэкендом.

### Технологии

Можно было бы добавить Loki к существующей Grafana, но как я понял, быстрого поиска локи не даст. Однако если понадобится сократить кол-во инструментов, то можно будет остановится на локи.

- Fluent bit
- OpenSearch
- OpenSearch Dashboards

| ----------------------- | ------------------- | ----------------- | ------- |
| Потребление памяти      | Очень низкое (~1MB) | Высокое (~500MB+) | Низкое  |
| Производительность      | Высокая             | Средняя           | Высокая |
| Трансформация логов     | Базовая             | Богатая           | Богатая |
| Интеграция с OpenSearch | Да                  | Да                | Да      |
| Интеграция с Loki       | Да                  | Да                | Да      |
| Сложность настройки     | Низкая              | Высокая           | Средняя |

|                         | OpenSearch                                              | Loki                                              |
| ----------------------- | ------------------------------------------------------- | ------------------------------------------------- |
| Хранение                | Индексирует все поля                                    | Индексирует только метки, текст хранится как есть |
| Поиск                   | Полнотекстовый, быстрый по любому полю                  | Медленнее — grep по тексту без индекса            |

| Когда выбирать          | Нужен быстрый поиск по любому полю (order_id, trace_id) | Уже есть Grafana, важна стоимость хранения        |
 
### Structured logging
 
Все сервисы пишут логи в JSON-формате — это позволяет OpenSearch индексировать каждое поле и искать по ним без парсинга текста.
 
### Correlation ID
 
`correlation_id` берётся из OpenTelemetry как `trace_id` — при наличии инструментирования он проставляется в логи автоматически.
 
### Индексы и политика хранения
 
Отдельный индекс на каждый сервис: `shop-api-logs`, `crm-api-logs`, `mes-api-logs`. Это позволяет настраивать разные политики хранения и права доступа независимо.
 
| Индекс        | Срок хранения | Обоснование                                       |
| ------------- | ------------- | ------------------------------------------------- |
| mes-api-logs  | 90 дней       | Расчёты и производство — основная зона инцидентов |
| shop-api-logs | 90 дней       | Полная цепочка заказа                             |
| crm-api-logs  | 90 дней       | Подтверждения и закрытие заказов                  |
| rabbitmq-logs | 30 дней       | Преимущественно операционные данные               |
 
Логи уровня ERROR дополнительно реплицируются в отдельный индекс `errors` со сроком хранения 180 дней — для анализа паттернов ошибок.
 
После истечения срока хранения логи автоматически удаляются через Index Lifecycle Management (ILM) в OpenSearch.
 
### Безопасность
 
**Чувствительные данные**
 
В логи не попадают полные персональные данные клиента: имя, адрес доставки, данные оплаты, содержимое 3D-файлов.
 
Если контекст требует присутствия персональных данных для диагностики — применяется маскировка:
- Email: `iv***@gmail.com`
- Телефон: `+7 (999) ***-**-11`
Вместо полных данных используются идентификаторы: `customer_id`, `order_id`, `operator_id`. Ревью полей логирования при каждом изменении как часть code review.
 
**Доступ к OpenSearch Dashboards**
 
- Аутентификация через логин/пароль с обязательным MFA
- Роли: `support` — поиск по `order_id` и `trace_id`, только чтение; `developer` — полный поиск, только чтение; `admin` — только DevOps, управление индексами и политиками
- OpenSearch развёрнут во внутренней сети, доступ снаружи только через VPN

## Система анализа логов
 
### Обнаружение аномалий
 
**Резкий рост числа заказов** — если количество событий `order_created` за минуту превышает среднее значение за последние 7 дней более чем в 5 раз, это может быть DDoS или некорректное поведение API-партнёра. Алерт DevOps для проверки и возможной блокировки.
 
**Резкий рост ошибок** — если доля ERROR-записей в индексе превышает 5% от общего числа записей за последние 5 минут. Алерт разработчику.
